# IBM Db2 database plugin HTTP API

The IBM Db2 database plugin is one of the supported plugins for the database
secrets engine. Unlike the SQL-style plugins, Db2 has no pure-Go driver and
native user management requires the `AUTH_NATIVE` security plugin that most
production deployments don't run, so this plugin does not issue dynamic
credentials. Instead it lets OpenBao track and rotate the value of a
statically-provisioned credential; see [Static
Roles](/docs/secrets/databases#static-roles) and the [IBM Db2 database
secrets engine](pathname:///docs/secrets/databases/db2) docs page for the
full picture.

## Configure connection

In addition to the parameters defined by the [Database
Secrets Engine](index.mdx#configure-connection), this plugin
has a number of parameters to further configure a connection.

| Method | Path                     |
| :----- | :----------------------- |
| `POST` | `/database/config/:name` |

### Parameters

- `url` `(string: "")` – Specifies the base URL of the Db2 REST API used
  for the reachability check (e.g. `http://db2-dbapi.example.com:50000`).
  When empty, the `Initialize`/`VerifyConnection` healthcheck is skipped
  entirely.

- `username` `(string: "")` – Specifies the username sent as HTTP Basic
  Auth credentials when calling the Db2 REST API's `/dbapi/v4/host_status`
  healthcheck endpoint.

- `password` `(string: "")` – Specifies the password corresponding to
  `username`.

- `ca_cert` `(string: "")` – Specifies a PEM-encoded CA certificate (or
  bundle) used to validate the Db2 REST API's TLS certificate.

- `ca_path` `(string: "")` – Specifies a filesystem path, on the host
  running the plugin, to a PEM-encoded CA certificate (or bundle) used to
  validate the Db2 REST API's TLS certificate.

- `client_cert` `(string: "")` – Specifies a PEM-encoded client certificate
  to present for mTLS to the Db2 REST API. Must be set together with
  `client_key`.

- `client_key` `(string: "")` – Specifies the PEM-encoded private key
  corresponding to `client_cert`. Must be set together with `client_cert`.

- `insecure` `(bool: false)` – Skips verification of the Db2 REST API's TLS
  certificate when connecting. Intended for development only.

This plugin does not accept `username_template` — Db2 credentials are
tracked under the literal `username` configured on a static role, and this
plugin does not generate its own usernames.

### Sample payload

```json
{
  "plugin_name": "db2-database-plugin",
  "allowed_roles": "app",
  "url": "http://db2-dbapi.example.com:50000",
  "username": "admin",
  "password": "admin"
}
```

### Sample request

```shell-session
$ curl \
    --header "X-Vault-Token: ..." \
    --request POST \
    --data @payload.json \
    http://127.0.0.1:8200/v1/database/config/db2
```

## Statements

Db2 has no dynamic-user statement language usable by this plugin — native
Db2 user management (`CREATE USER` / `ALTER USER` / `DROP USER`) requires
the `AUTH_NATIVE` security plugin that most production deployments don't
run, and this plugin never attempts it. As a result the plugin does not
read or use `creation_statements`, `revocation_statements`,
`rollback_statements`, or `root_rotation_statements` at all; any value
supplied for these fields is accepted by the database secrets engine
framework but ignored.

- Dynamic roles (`bao write database/roles/:name` followed by
  `bao read database/creds/:name`) are **not supported**. Creating a
  dynamic role succeeds, but reading credentials from it always fails with:

  ```text
  dynamic credentials are not supported by this Db2 plugin (no pure-Go
  driver + most prod deployments delegate auth to OS or LDAP); use
  static-roles to track a manually-provisioned credential, or run a
  sidecar that applies the rotated value to the Db2 auth plugin
  ```

- Static roles are the supported credential-tracking mechanism. Configure
  one with a `username` that already exists as an OS user or LDAP
  identity, and a `rotation_period`:

  ```shell-session
  $ bao write database/static-roles/app \
      db_name=db2 \
      username=APP \
      rotation_period=24h
  ```

  On each rotation OpenBao generates a new password and stores it — it
  does not push the value to the Db2 server. An external system must apply
  the same password to the OS user, LDAP identity, or `AUTH_NATIVE` plugin
  backing that credential to keep it in sync.

- Root credential rotation (`bao write -force database/rotate-root/:name`)
  behaves the same way: OpenBao generates and stores a new root
  `username`/`password` pair in the connection configuration without
  contacting the server.
