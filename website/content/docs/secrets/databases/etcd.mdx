# etcd database secrets engine

etcd is one of the supported plugins for the database secrets engine. This
plugin generates dynamic credentials against an [etcd](https://etcd.io/)
cluster's built-in v3 Auth API, using the official etcd Go client. It also
supports [Static Roles](index.mdx#static-roles).

See the [database secrets engine](index.mdx) docs for
more information about setting up the database secrets engine.

Like the Neo4j plugin, `creation_statements` is a single JSON document
listing pre-existing etcd role names to grant the new user, rather than a
semicolon-separated list of statements. Under the hood the plugin calls
etcd's `UserAdd` followed by one `UserGrantRole` per listed role. Roles
referenced by `creation_statements` must already exist on the cluster (for
example via `etcdctl role add`) — this plugin does not create roles, only
users and role grants.

## Capabilities

| Plugin Name            | Root Credential Rotation | Dynamic Roles | Static Roles | Username Customization |
| ----------------------- | ------------------------- | -------------- | -------------- | ------------------------ |
| `etcd-database-plugin` | Yes                       | Yes            | Yes            | Yes                      |

## Setup

1.  Enable the database secrets engine if it is not already enabled:

    ```shell-session
    $ bao secrets enable database
    Success! Enabled the database secrets engine at: database/
    ```

    By default, the secrets engine will enable at the name of the engine. To
    enable the secrets engine at a different path, use the `-path` argument.

1.  Configure OpenBao with the proper plugin and connection information. The
    root credentials only need to be provided if authentication is enabled
    on the cluster:

    ```shell-session
    $ bao write database/config/etcd \
        plugin_name="etcd-database-plugin" \
        allowed_roles="reader" \
        endpoints="https://etcd.example.com:2379" \
        username="root" \
        password="password"
    Success! Data written to: database/config/etcd
    ```

1.  Configure a role that maps a name in OpenBao to an etcd role-grant
    document to execute to create the database credential. The roles listed
    must already exist on the cluster:

    ```shell-session
    $ bao write database/roles/reader \
        db_name="etcd" \
        creation_statements='{"roles":["reader"]}' \
        default_ttl="1h" \
        max_ttl="24h"
    Success! Data written to: database/roles/reader
    ```

## Usage

After the secrets engine is configured and a user/machine has an OpenBao token with
the proper permission, it can generate credentials.

1.  Generate a new credential by reading from the `/creds` endpoint with the name
    of the role:

    ```shell-session
    $ bao read database/creds/reader
    Key                Value
    ---                -----
    lease_id           database/creds/reader/2f6a614c-4aa2-7b19-24b9-ad944a8d4de6
    lease_duration     1h
    lease_renewable    true
    password           SsnoaA-8Tv4t34f41baD
    username           v-token-reader-x7g2kf8s1a2b-1717000000
    ```

## etcd-specific notes

- **No native credential expiry**: etcd has no expiry concept on users, so
  lease expiry for dynamic roles is enforced purely by OpenBao revoking the
  lease (`UserDelete`), not by the database itself.
- **Partial-failure cleanup**: `UserAdd` is not transactional with the
  subsequent `UserGrantRole` calls. If any role grant fails (for example,
  the role does not exist), the plugin deletes the just-created user before
  returning the error, so no half-configured user is left behind.
- **Idempotent revocation**: deleting a user that no longer exists is
  treated as success, so lease revocation is safe to retry.
- **`endpoints` accepts a comma-separated list**: point it at every member
  you want the client to be able to reach, e.g.
  `https://etcd1:2379,https://etcd2:2379,https://etcd3:2379`.
