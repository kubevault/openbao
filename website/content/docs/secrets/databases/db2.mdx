# IBM Db2 database secrets engine

IBM Db2 is one of the supported plugins for the database secrets engine, but
it works differently from the SQL-style plugins. Two facts about Db2 rule
out a dynamic-credentials implementation:

- There is no pure-Go Db2 driver. The canonical client
  (`github.com/ibmdb/go_ibm_db`) requires CGO and the IBM CLI Driver
  installed on the build host, which conflicts with OpenBao's
  `CGO_ENABLED=0` build target.
- Native Db2 user management (`CREATE USER` / `ALTER USER` / `DROP USER`)
  requires the `AUTH_NATIVE` security plugin to be loaded. Most production
  Db2 deployments delegate authentication to OS users or LDAP instead, so
  implementing dynamic credentials against `AUTH_NATIVE` would be
  misleading for the typical deployment.

Instead, `db2-database-plugin` lets OpenBao be the source of truth for a
credential's value and rotation schedule, using [Static
Roles](index.mdx#static-roles) as the primary supported workflow:

- `Initialize` (and `VerifyConnection`) optionally call the configured Db2
  REST API's `/dbapi/v4/host_status` endpoint with HTTP Basic Auth to
  confirm the server is reachable. If `url` is left empty, this check is
  skipped entirely.
- Dynamic credentials (`bao read database/creds/...`) are **not
  supported**. `NewUser` always returns an explicit error telling the
  operator to use static roles, or run a sidecar that applies the rotated
  value to the Db2 auth plugin.
- Static-role rotation (`UpdateUser`) does not contact the Db2 server at
  all. It validates the request and returns success so that OpenBao tracks
  the new password and emits the usual audit events, but applying that
  password to the OS user, LDAP identity, or `AUTH_NATIVE` plugin backing
  Db2 authentication is left to an external system — a sidecar or
  configuration-management tool that watches OpenBao and pushes the
  value — which is out of scope for this plugin.
- `DeleteUser` is likewise a no-op against the server.

This is the same shape used by the Memcached, Qdrant, and Weaviate plugins
in this repo for servers with no runtime user-management API.

See the [database secrets engine](index.mdx) docs for more information about
setting up the database secrets engine.

## Capabilities

| Plugin Name            | Root Credential Rotation | Dynamic Roles | Static Roles | Username Customization |
| ----------------------- | --------------------------- | ---------------- | --------------- | ------------------------- |
| `db2-database-plugin`  | Yes                       | No             | Yes           | No                      |

Both "Root Credential Rotation" and "Static Roles" here are OpenBao-side
bookkeeping only: `bao write -force database/rotate-root/<name>` and
static-role rotation both succeed and update the password OpenBao tracks,
but neither pushes the new password to the Db2 server. An operator or
sidecar must apply the same value to the OS user, LDAP identity, or
`AUTH_NATIVE` plugin backing that Db2 credential to keep it in sync.
`db2-database-plugin` does not support `username_template` — usernames are
the literal value configured on the static role.

## Setup

1.  Enable the database secrets engine if it is not already enabled:

    ```shell-session
    $ bao secrets enable database
    Success! Enabled the database secrets engine at: database/
    ```

    By default, the secrets engine will enable at the name of the engine. To
    enable the secrets engine at a different path, use the `-path` argument.

1.  Configure OpenBao with the proper plugin and connection information:

    ```shell-session
    $ bao write database/config/db2 \
        plugin_name="db2-database-plugin" \
        url="http://db2-dbapi.example.com:50000" \
        username="admin" \
        password="admin" \
        allowed_roles="app"
    Success! Data written to: database/config/db2
    ```

    `url` is optional — when it is left unset, the reachability check
    performed on `Initialize`/`VerifyConnection` is skipped.

1.  Configure a static role that maps a name in OpenBao to a
    manually-provisioned Db2 username (an existing OS or LDAP identity),
    and a rotation period for OpenBao to generate and track a new password
    on:

    ```shell-session
    $ bao write database/static-roles/app \
        db_name="db2" \
        username="APP" \
        rotation_period="24h"
    Success! Data written to: database/static-roles/app
    ```

    Attempting to create a dynamic role and read `database/creds/<role>`
    against this plugin fails with an explicit "dynamic credentials are not
    supported" error — use static roles as shown above instead.

## Usage

After the secrets engine is configured and a user/machine has an OpenBao
token with the proper permission, it can read the current static
credential.

1.  Read the tracked password from the `/static-creds` endpoint with the
    name of the role:

    ```shell-session
    $ bao read database/static-creds/app
    Key                    Value
    ---                    -----
    last_vault_rotation    2026-08-07T09:00:00.000000000Z
    password               SsnoaA-8Tv4t34f41baD
    rotation_period        24h
    ttl                    23h59m12s
    username               APP
    ```

    Apply this password to the Db2 server's `AUTH_NATIVE` plugin, OS user,
    or LDAP identity out of band (for example, from a sidecar or
    configuration-management run) to keep the server in sync with OpenBao.
